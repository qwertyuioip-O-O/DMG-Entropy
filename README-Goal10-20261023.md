# Cumulative +10% encode and decode goal — 2026-10-23

The user requested a further 10% throughput improvement in each direction, allowing gains to accumulate gradually. The fixed anchor is the accepted LTO + audited raw-scratch build at the start of this request, SHA256 `7c466d55510493aa2366aa310f50583083a161f88304f64e2941089ca9333918`. Its source snapshot and build script remain unchanged. A copy of that Linux x86-64 executable is retained under `benchmarks-goal10-20261023/anchor/` to keep future comparisons grounded in the same binary.

Cumulative progress is measured directly against this anchor. Percentages from older studies are not added or multiplied. The primary aggregation remains the equal-dataset geometric mean of paired phase-time throughput ratios. The goal is a ratio of at least 1.10 in BOTH encoding and decoding, not just a combined encode/decode average.

## Two cumulative stages

Stage1 (`g10rank`) replaces `std::sort` of candidate rank records with bounded score buckets. A single 129-entry head array covers the existing proven score range −64..64; linked candidate indices and class counts produce the same strictly-better counts. All members of a tied score group are evaluated before updating class counts, preserving tie semantics. Only observed min..max score buckets are scanned. This avoids the previous large class×score histogram design as well as general comparison sorting.

Stage2 (`g10mob`) adds exact bitboard slider-mobility counting. Existing ray tables and nearest blockers identify available squares, then popcount counts squares excluding friendly occupancy. Quiet bishop moves use the correct post-move occupancy and friendly occupancy. Original feature thresholds and probability calculations are unchanged. Stage2 includes stage1; it is not an independently composable percentage gain.

`tools/generate_goal10.py` derives isolated source variants from the frozen scratch implementation. Neither stage includes the earlier optional attack-union, incremental-ray or PGO experiments. All normal builds keep the retained `-O3 -flto=1` flags without architecture-specific ISA or fast-math flags.

## Correctness

`DMT_VERIFY_GOAL10` retains the original sorting-based rank and square-walking mobility implementations as independent feature oracles. Every computed rank-feature array and positional-feature array, including quiet flags, is compared directly with its original reference. The oracle executable passed complete mode3 evaluation on all three datasets, with encode/decode and repeated-byte validation.

The three-way release screening also packs all five modes × all three datasets with every implementation. All three archives must match byte-for-byte in each case, and each pack validates its own roundtrip. The stage2 executable runs the existing 1,226-check suite (empty/short streams, malformed data, CRC, truncation, wrong model, LUT and R18 identity). No learned coefficients, observation order or archive framing is changed.

## Measurement and selection

The goal and binary anchor were recorded before timing. CPU0 screening uses three rotated mirrored six-process blocks per dataset: ABC CBA, BCA ACB, CAB BAC. Each implementation occupies every mirrored position pair once. Across three datasets this is 54 actual CLI processes. Each process warms and runs three timed iterations per direction with byte/roundtrip validation. Whole blocks are the unit of comparison; individual inner iterations are not independent samples.

Both stage1 and stage2 are measured directly against the anchor. Among candidates positive in both aggregate directions, prefer the larger minimum of encode/decode aggregate gains. This screening selection is exploratory; it is followed by a fresh paired CPU1 confirmation of the selected candidate against the same fixed anchor. Confirmation uses four alternating ABBA/BAAB blocks per dataset: 48 CLI processes, 12 blocks per direction. Full correctness tests are reused for identical executable hashes; the CLI warm/repetition checks still run in every process. Confirmation records per-child whole-process CPU time and cgroup counters in addition to CLI phase wall times.

The confirmation's two direction gains determine the reported cumulative progress and +10% threshold status. Screening and confirmation percentages are not compounded. A result remains limited to these datasets, host and exposed cores; no universal hardware or statistical-significance claim is made. Builds, oracle checks, training and other benchmarks do not run concurrently with timing.

A fresh gprof profile of the anchor was also collected before candidate timing. LTO/inlining can merge or misattribute symbols and call counts, so the raw profile is diagnostic only; it does not prove a precise production cost fraction for an individual function. Candidate decisions use ordinary uninstrumented CLI timings.
