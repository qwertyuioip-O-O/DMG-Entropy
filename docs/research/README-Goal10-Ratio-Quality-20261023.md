# Exact opportunity division and measurement quality — 2026-10-23

No new codec candidate is adopted. The portable index-rank build remains selected. This attempt does not establish an additional speedup or completion of the two-direction +10% wall-time goal.

Two candidates were implemented. Dense opportunity pages lost to the retained control in the same 54-call screen (encode -0.327513%, decode -3.248830%). See README-Goal10-Dense-20261023.md. The second candidate changes only one opportunity-ratio division, retaining full-key pages and the selected index-rank features.

The exact ratio is n/d, where n=(uint64(actual)+16384)*1024 and d=uint64(expected)+16384. For the entire uint32 counter domain, n<2^43, d<2^33 and quotient<2^29. IEEE arithmetic with at least 53 significand digits represents both integer operands exactly and estimates the quotient to less than one integer. A uint64 product and one exact correction recover the original integer floor; product<2^62 avoids overflow. Unsupported precision/IEC559 types use the original integer division. The documented builds use ordinary strict floating-point options, without fast-math or CPU-native ISA flags. No floating approximation is stored in learned state.

The actual production helper was extracted and compared with native uint64 division on 7,194,704 inputs: a 2048x2048 exhaustive grid, full uint32 random values, extreme counters and probes near integer quotient boundaries. All passed. Reverse substitution of the helper and its single call reproduces the retained core exactly. Whole-codec validation for each candidate passed all 15 three-arm mode/dataset byte identities and all 1,226 existing checks. Coefficients and archive framing remain unchanged.

The ratio wall-time screen used CPU2, chosen before timing because the preceding CPU0 screen was variable. It preserved all 54 CLI calls, with no rows trimmed. The ratio point estimates versus fixed anchor were encode +15.631172%, decode -0.437211%; against retained index ranks, encode +4.250468%, decode +16.386767%. These are noisy observations, not validated speedups. The predeclared positive-primary/balanced-gain rule did not select this candidate for fresh wall confirmation.

A separate CPU-phase diagnostic kept all three executable hashes unchanged. A small Linux measurement-only shared object redirects CLOCK_MONOTONIC to CLOCK_PROCESS_CPUTIME_ID only inside explicitly launched benchmark children. Python driver clocks and CLOCK_REALTIME remain wall time. The default production build never loads it. The exported interposition surface is only clock_gettime. A C++ steady_clock probe verified that sleep contributes wall time but almost no redirected CPU time; three preloaded mode3 packs matched saved native-clock archives. Each subsequent speed invocation also checked repeated bytes and roundtrip.

The diagnostic comprised 18 calls, one mirrored three-arm block per dataset on CPU1. CPU phase records were consistent with external child resource CPU totals. However, CPU time itself also varied strongly, so simple process waiting cannot be assumed to explain all variation. Median total CPU/wall was about 0.9972. No underlying environmental cause has been established. CPU diagnostics remain separate from the wall-time goal and do not redefine its threshold or mark it complete.

A conservative quality audit now rejects experiments with a same-binary, same-data phase max/min ratio above1.25, fewer than two repeat samples, or an inconsistent CPU clock. This is a large-variation gate, not a confidence interval or sufficient proof of a small gain. The threshold was introduced after examining these trials, so their audit is descriptive, not preregistered. For future runs benchmark_goal10_guarded.py writes the threshold into the protocol before timing, verifies the fixed anchor hash, preserves every row and exits nonzero if quality fails. Passing the gate still requires a valid comparison and fresh confirmation. No outlier rows are discarded.

Audit failed for all three records: dense wall 17/18 variable groups, ratio wall 18/18, CPU diagnostic 4/18. Worst repeat max/min across these records: 16.533. The guard passed five behavior tests, including an apparent gain with unstable repeats, the exact threshold boundary, invalid CPU timing and unchanged raw CSV hashes. A changed goal anchor was rejected before any codec work.

The prior +11.519372% encode/+7.175028% decode values remain historical CPU1 wall-phase point estimates for the selected index build. They were not newly reproduced by this attempt. The next performance comparison should pass a repeatability check before interpreting a small delta.
