# DMG-Entropy v0.5 — Stage-conditioned models and forcing-check experiment

**Date:** 2026-10-20. Language: C++20. Corpus and test material provided in this archive. No pretrained model or external statistical weights.

## Experimental question

Can opening/middlegame/endgame context, without offline training, beat the already verified tactical+check-filter model while maintaining usable throughput?

The **unexpected result**: simple phase bonuses did not help consistently. Explicitly weighting moves that deliver check, tested independently of phase, **did** yield a small gain.

## Baselines and 23-game paired comparison

All 23 games correspond to `examples/heldout/SOURCES.csv`, 1,718 legal plies. Bit counts are obtained from fully encoded, successfully decoded files, not estimated entropy only. Each encoded game includes a 16-byte header, and physical payload uses whole bytes.

| `phase` | 4.873108 | 6.616997 | 8,372 | 1,421 |
| `phase-tactical` | 4.624563 | 6.393481 | 7,945 | 1,373 |
| `phase-check` | 4.366123 | 6.123399 | 7,501 | 1,315 |

The mode `best` independently runs several compressors and takes the smallest payload for each whole game, so it is *not* a competitive speed baseline. It achieved 4.25262 payload bits/ply, but its encoder is orders of magnitude slower than a single model. Do not equate that per-game selection with a practical single-pass codec.

## What the new features mean

- **Opening:** at high retained non-pawn material (phase >= 19) and early ply < 30, modest additional weight to central pawn moves, developing knights/bishops, castling; reduced queen/rook quiet moves.
- **Middle:** a modest capture/central-pawn preference otherwise.
- **Endgame:** phase <= 8, extra advancing-pawn/king-activity/promotion bonuses.
- **Forcing-check:** simulate candidate move, compute whether current mover attacks opposing king afterwards, and add either +24 (`check-signal`) or +12 (`check-signal-light`) to candidate integer weight. This is an explicit, relatively expensive state feature.

The `check-signal-light` model retains precisely the v0.4 `tactical-check` structure (with complete move filtering only when the current king is already in check) and adds **only** the checking-move signal. Thus the improvement can be causally attributed to that incremental feature on this corpus, while the phase bonuses themselves cannot.

## Per-game stability

On the 23 recorded games compared to `tactical-check`, `check-signal-light` compressed **16 better, 6 worse, 1 tied**. Savings in payload bits / total plies by subgroup: historical 0.08686, modern famous 0.02385, ordinary online 0.09524 bit/ply, with only 3 online games and strong small-sample caveats.

Paired nonparametric bootstrap using 10,000 *whole-game* resamples with seed 24145 yields a 95% percentile interval **0.03236 to 0.10720 bit/ply** improvement for the selected 23-game set. This is **not a guarantee** of performance in the chess population and was not generated by independent random sampling.

## Performance (same corpus, same executable)

Single run of median-of-5 timing harness; each run repeats whole corpus eight times. Output: `results-v0.5/speed_all23.csv`. Rates in million plies per second, excluding disk I/O.

| Mode | Encode | Decode |
|---|---:|---:|
| `tactical-check` | 0.569 | 0.582 |
| `phase-middle` | 0.579 | 0.542 |
| `phase-forcing` | 0.317 | 0.323 |
| `check-signal-light` | 0.335 | 0.316 |

`check-signal-light` retains only about 59% of the baseline encoding throughput and about 54% of decoding throughput. Thus v0.5 is a **modest compression-versus-speed tradeoff**, not a Pareto improvement. Phase material count is computed once per state; explicit checking-signal evaluation is still the major cost. These timings are not transferable hardware estimates.

## Synthetic random legal game sanity check

CLI benchmark (seed 24145, 50 games, 80-ply limit, 3,967 resulting plies):

| Mode | Payload bits/ply |
|---|---:|
| `uniform` | 5.006 |
| `tactical-check` | 5.475 |
| `phase-middle` | 5.491 |
| `check-signal-light` | 5.464 |

Random legal-choice games do not match human selection tendencies. Weighted models are **worse** than uniform here, as expected. Do not infer improvement from synthetic data.

## Correctness and backwards compatibility

- `ctest` Release: PASS, incl. 60 randomly generated legal games, castling, en passant, underpromotion, pinned piece, illegal-move rejection, and legacy v0.2 stream fixture.
- `ctest` with AddressSanitizer + UndefinedBehaviorSanitizer: PASS.
- 23 games × 20 methods = **460** complete byte-stream encoder→decoder UCI exact round trips; new modes independently re-encoded to check bit-for-bit determinism.
- New mode identifiers are 16–24; v0.5 decodes older RMC1 compressed games. Old decoders do not recognize the new IDs.
- File format has no checksum and should not be treated as tamper-detecting.

## Interpretation and next experiment

The stage-only hypothesis is **not supported as a large win** on this data. Checking-move detection works modestly, but slow candidate-by-candidate board simulation is not the right final design.

Priority for v0.6: compute the `gives_check` signal using lightweight incremental bitboards / king rays rather than a full `Position` copy plus attack scan for every move; preserve output byte-for-byte for identical states and encoding mode. In parallel obtain randomly sampled modern human games (stratified by Elo / length / time control). Only then revisit the goal of 3.5–3.9 payload bits/ply with a stronger low-cost conditional model. The file overhead (6.049 full bits/ply here) must also be tackled separately, potentially via batching multiple games per container.

## Reproduction

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
python3 tools/validate_heldout.py --binary build/rmc --out results-v0.5
python3 tools/analyze_v05.py
./build/rmc_human_bench examples/heldout/*.uci
./build/rmc bench 50 80 24145
```

**Sampling limits:** Despite attempts, a larger externally hosted PGN archive could not be downloaded from the current tool environment. Earlier v0.4's 23-game validation corpus was reused; therefore v0.5's test is a **controlled paired comparison on existing selected data**, not a wholly fresh independent corpus.
