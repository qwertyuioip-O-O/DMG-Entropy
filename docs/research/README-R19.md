# DMT19 — 보정 통합, 재학습, 대응 특징 검증

2026-10-22. R18의 두 보정을 한 번에 계산하는 경로를 만들고, 새 계산식에 맞춰 다시 학습했다.
선택용 자료에서 고정한 대응 특징 모델(mode3)이 기존 세계선수권13판 중반 CDF 평균3.93231→3.89298bit/반수를 기록했다. 이 회귀 자료에서는3.9 이하이나, 여러 번 확인한13판이므로 범용/독립 엘리트 검증의 달성이라고 주장하지 않는다.
새422판 실제 파일도12,350→12,328byte(0.178%)로 작아졌다. 속도는 측정에 따라 엇갈려 회복을 확정하지 않는다. 일반 pack 기본234와 기존 형식은 유지하고 별도 연구용 D19P 옵션으로 제공한다.

## 보정 경로를 합쳤다

R18은 기존 공동 분포→전역 보정/LUT/정규화→문맥 보정/LUT/정규화 순서였다. 새 모드에서 합친 것은 이 추가 보정 단계의 정규화이며, 기반 모델 내부의 기존 혼합/정규화를 모두 없앴다는 뜻은 아니다.

| mode | 의미 | 중반 추가 보정 |
|---|---|---|
| 0 | R18 기준 경로 | 기존 두 단계 그대로 |
| 1 | 기존 가중치 그대로 통합 | 전역/문맥 점수 각각±128 제한, 두 LUT 곱을 적용하고 한 번 정규화 |
| 2 | 재학습한 문맥 통합 | 문맥별672계수, 점수 합을±256로 제한, 한 LUT/한 정규화 |
| 3 | 통합+대응 특징: 주 후보 | mode2 구조+기물×대응 서명48계수 |
| 4 | 같은 크기의 기하 대조군 | mode2 구조+기물×도착 file48계수 |

주 후보의 계산은 다음과 같다. 모든 합법 후보의 공동 분포를 유지하며 출발 기물을 독립적으로 먼저 고르지 않는다.

```text
score = 문맥 테이블의 기존 특징5개 합 + 기물별 대응 서명값
weight = 기반 공동 분포의 weight × LUT[clamp(score, -256, 256)]
CDF = weight들을 한 번 정규화
```

R18은 두 보정의 제한을 합치면 최대±256 범위였고 새 모델도 최종±256 범위를 사용한다. 단순한 범위 확대로 효과를 설명하지 않도록 같은 범위/LUT/정규화의 mode2/4와 비교했다.
mode1도 중간 정규화를 생략하여 반올림이 바뀌므로 R18과 비트 동일하다고 주장하지 않는다. 주 후보는 중반 점수 계산에서 전역/문맥10개 조회 대신 기존5개+대응1개를 조회한다.
주 후보 테이블720개 int16=1,440byte이며, 점수 계산에 사용하는 R18 전역168+문맥672=840개보다 적다. 다만513개 uint32 LUT(약2KiB)를 사용하고 연구 도구에는 기준 모델도 함께 들어 있으므로 실행 파일 전체 메모리가 줄었다고 주장하지 않는다.

## 남은 오류와 대응 가설

개발457판에서 R18을 재생하고, 대응 서명별 중반 손실을 분해했다. 서명은 이미 계산된 플래그의 되잡기(bit5), 위협받던 기물을 공격받지 않는 칸으로 옮김(bit1), 체크 주기(bit8)의3비트 조합이다.
새로운 공격 맵이나 탐색을 추가하지 않는다. 탈출 플래그가 반드시 직전 수가 새로 만든 위협이라는 뜻은 아니며, 체크 주기는 체크 대응과 다르다.
세 플래그가 모두0인 그룹8,243수는 평균4.26654bit였고, 되잡기만 있는1,686수는1.14721bit였다. 즉 대응 수 자체가 가장 어려운 부분이라는 가설은 지지되지 않았다. 남은 큰 손실은 세 플래그가 없는 그룹에 집중된다.
그럼에도 대응 조합의 확률 질량 보정이 유효한지는 저비용 후보로 시험했다. 단순히 계수48개를 늘린 효과와 구분하려고 같은 크기의 도착 file 특징도 사전에 비교했다. 개별 기보의 인간 의도를 추론했다고 주장하지 않는다.

## 학습/선택/동결

- 학습은 R13 dev457판/31,585반수의 중반14,330위치/470,656합법 후보만 사용했다.
- 고정 R18의 실제 재생 상태에서 보정 전 기반 공동 분포를 추출했다. 새 모델을 넣었을 때 달라지는 모든 온라인 상태 경로를 미분한 것은 아니며 실제 코덱 평가로 확인했다.
- mode2/3/4 각각 정규화1e-5/1e-4/1e-3을 학습했다. 초기값은 R17 전역값+R18 문맥값을 합친 값, 추가48계수는0이다. 총9개 학습 후보+1개 비학습 통합 후보를 비교했다.
- 선택은 R13 select153판의 실제 byte, 동률이면 payload bit로만 했다. 주 후보는 mode3/0.001, 순수 통합 mode1은 별도 속도 비교용으로 사전에 고정했다.
- mode3/0.001은88회에 수렴했다. 1e-5의3모델과 mode4/1e-4는300회 제한에 도달했고 수렴으로 표시하지 않았다. 선택된 주 후보와 두 대조군은 수렴한 모델이다.
- 선택용: R18 34,587bit/4,500byte → 주 후보34,551bit/4,495byte. 순수 통합은34,586bit/4,500byte였다.
- plain 대조는 mode2/0.0001, 기하 대조는 mode4/0.001로 선택했다. 두 대조군도 새 자료 평가 전에 FREEZE.json에 해시/설정을 기록했다.
- 그 뒤 새 기보/세계선수권 결과를 보고 후보나 가중치를 바꾸지 않았다. 모델 동결 뒤 변경은 동일 builtin 테이블 연결, 검사/CLI 기록뿐이며 encode/decode 본문 접두부는 동결 스냅샷과 동일하다.

## 압축 결과

중반 수치는 해당 국면에서 실제 부호화에 사용하는 CDF의 평균 -log2 확률이다. 국면별 실제 바이트를 분리해 저장한 수치가 아니다. 실제 파일은 모든 국면, 게임 길이, 헤더, CRC를 포함하며 D18P와 D19P 프레이밍 길이는 같다.

| 자료 | R18 byte | 주 후보 byte | 감소 | R18 중반 CDF bit/반수 | 주 후보 중반 CDF |
|---|---:|---:|---:|---:|---:|
| 새422판: 동결 후 평가 | 12,350 | 12,328 | 0.178% | 3.26983 | 3.25661 |
| 세계선수권13판: 기존 회귀 | 581 | 579 | 0.344% | 3.93231 | 3.89298 |
| 이전456판: 회귀 | 12,888 | 12,873 | 0.116% | 3.25050 | 3.24119 |
| 이전439판: 회귀 | 12,658 | 12,639 | 0.150% | 3.26517 | 3.25389 |
| 이전202판: 회귀 | 6,237 | 6,229 | 0.128% | 3.28716 | 3.27716 |
| 인간4판: 회귀 | 262 | 261 | 0.382% | 4.06370 | 4.03936 |

세계선수권은13판/1,155반수 중 중반579반수의 평균이다. 각 개별 대국이 모두3.9 이하라는 뜻은 아니다. R16 strong 4.08905→R17 3.98508→R18 3.93231→현재3.89298로 내려왔으나 이 고정 회귀 자료를 여러 번 사용했다. 새로운 엘리트 기보로 확인하기 전 범용3.9 달성을 선언하지 않는다.
순수 통합 mode1의 압축 변화는 매우 작았다. 새422판은95,121→95,120bit, 이전456판은99,158→99,161bit였다. 기존 가중치를 합치기만 해도 항상 더 작아지는 것은 아니다.

## 새 평가 자료와 작은 파일

새 자료는4개 신규 대회(40M6JQIT/wmiq4xGv/fpIHnJma/4K3Q2R8F)의422판/28,975반수/603명이다. 대회 목록 스냅샷에서 진행 중인 대회를 골랐지만 이미 완료된 게임만 사용했다.
표준 초기 배치,16반수 이상, 완료 결과, 파싱 오류 없는 게임만 사용하고 이전 전체 UCI 수열과 내부 중복을 제거했다. 출처당 최대120판을 UCI SHA256 순서로 고른다. 특수 초기 위치의 테마 대회는 제외했다.
dev 선수15명/select6명이 겹치므로 선수 단위 독립 검증은 아니다. 대회 출처와 전체 기보 수열은 과거 자료와 다르다. 주로 온라인 속기/래피드 자료이므로 엘리트 클래식 전체를 대표하지 않는다.
API 주소/다운로드 해시/기보 헤더/고정 UCI는 data-r19에 포함한다. 이후 API 응답이 달라도 포함된 UCI로 재현한다. 네 출처를 따로 초기화해도 주 후보는 각각8/2/5/6byte 작아졌다.
같은422판을 파일당1/10/30/120/422판으로 나눈 특성 분석도 했다. 한 판씩 압축한 합계21,271→21,240byte, 중반 CDF3.55387→3.53894bit다. 독립 자료가 추가된 것은 아니다.
blocks.csv는 동일 primary 테이블의 의미 있는 mode0/3 비교만 추렸다. blocks-raw.csv의 mode2/4는 primary 테이블을 다른 키로 해석한 비학습 진단이며 별도로 동결한 plain/geometry 대조군과 혼동하면 안 된다.

## 속도: 회복 확정은 보류

모든 빌드/검사 종료 후 같은 실행 파일에서 R18 기준(mode0), 순수 통합(mode1), 주 후보(mode3)를6회 균형 순서로 측정했다. 각 모드는 각 순서 위치에2회씩 배치했다. 매 프로세스에서 예열 복원 후 인코딩3회·디코딩3회와 결정성/복원 검사를 했다.

| 자료/모드 | 인코딩 처리량 변화 짝별 중앙값 | 디코딩 처리량 변화 짝별 중앙값 | 새 인코딩/디코딩 반수/초 중앙값 |
|---|---:|---:|---:|
| new / 1 | -7.09% | +4.89% | 40,255 / 41,943 |
| new / 3 | -0.57% | +0.85% | 39,600 / 40,926 |
| r18 / 1 | +3.25% | +2.19% | 45,187 / 43,360 |
| r18 / 3 | +7.24% | +2.48% | 47,350 / 45,051 |

주 후보는 새422판에서 각각3/6회만 빨랐고, 이전456판에서는 인코딩5/6·디코딩4/6회 빨랐다. 전체 실행에서 일관된 속도 회복을 확인했다고 말할 수 없다. 이번 환경에서60~70K 목표도 확인하지 못했다.
추가로 동일 encode/decode 본문을 복사한 진단 실행 파일에서 허용 CPU 하나에 고정하고8회 ABBA/BAAB 순서로 측정했다. 인코딩/디코딩을 따로 비교하고 검사는 시간 밖에서 수행했다.

CPU 시간 기준 처리량 변화 중앙값은 인코딩+2.29%(5/8회 빠름), 디코딩+5.64%(6/8회 빠름)이었다. 벽시계 시간도 유사했지만 일부 회차는 느렸다.
이는 개선 징후일 뿐 기존 CLI 측정의 불일치를 덮어쓰는 증거로 사용하지 않는다. 진단 실행 파일은 코드 본문이 동일하지만 명령행 도구와 코드 배치가 같다는 보장은 없다. build --paired는 본문 접두부의 일치를 검사한다. 안정된 대상 CPU에서 추가 확인 전 속도 동시 우세/기본 승격을 주장하지 않는다.

## 형식/검증

- D19P v1은 모드0..4,720계수 테이블 CRC32 식별값, 전체 파일 CRC를 사용한다. CRC는 보안 해시가 아니다. builtin과 같은 파일 계수로 동일 스트림을 만든다.
- 계수는 int16 범위±256, 최종 학습 모델 점수는±256로 제한한다. 새513항 uint32 LUT는 중앙257항이 기존 LUT와 같고 전체 단조성/양 끝256·65,536을 검사했다.
- 최종1226개 검사 통과: 모든 모드, 빈 묶음·빈 판·한 수·인간 기보 복원, CRC 변경/잘린 입력/다른 테이블 거절, R18 payload 항등성, LUT 범위/단조성/기존 값 일치.
- 독립적으로 작성한 통합 키 계산이 기존 R18과 개발 자료의470,656후보에서 키/합법 수 순서/전술 플래그가 일치했다. 최종 빌드에서도 인간4판9,045후보를 확인했다.
- 학습기의 방향 미분 수치 검사 오차는2.89e-11였다. 실제 코덱은 정수 LUT/양자화를 사용하므로 연속 학습 목적함수와 완전히 같다는 뜻은 아니다.
- 새/기존 평가와 출처별 결과의 결정성과 복원을 확인했다. 최종 표 완전성 검사에서 한 출처 CSV에 마지막2행이 없음을 발견해 재실행했고 최초 평가 표와 완전히 일치했다. 누락 원인은 판명하지 못했다. 불완전 기록과 csv-verification.json도 보관했다.
- 실제 새422판/세계선수권/이전456판 pack/unpack UCI 및 builtin/파일 테이블의 전체 파일 일치를 확인했다. 기준 파일은 기존 R18 실행 파일로 직접 생성했다.
- 이전 src/include17개 파일은 R18과 바이트 단위로 같다. R18 도구에는 참조로 포함할 때 main을 제외하는 가드만 추가했다. 기존 형식/일반 pack 기본234는 유지한다. 이전508개 호환 검사를 새로 전부 돌렸다고 주장하지 않는다.
- 동결 스냅샷/소스 해시/모델 해시/원자료/반복 측정/실패 후보를 함께 보관한다.

python3 tools/build_r19.py --out build-r19

최종 빌드 후 재현 스크립트의 실행 부분을 순서대로 수행했다. 이후 표 완전성 보완, 실제 파일 검증, CPU 고정 진단은 별도로 실행했다. 최종 휴대용 스크립트를 빌드부터 한 번에 모두 다시 실행한 것은 아니다. 학습 환경에 따라 마지막 반올림이 달라질 수 있어 frozen 모델 해시를 기준으로 비교한다.
