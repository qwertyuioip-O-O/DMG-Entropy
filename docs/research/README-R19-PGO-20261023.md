# R19 LTO + PGO experiment — 2026-10-23

The user accepted the aggregate LTO gain and asked to retain it while continuing improvement. The baseline for this experiment is therefore the existing LTO direct-output executable, not the older ordinary build. General pack profile234 is a separate default and remains unchanged.

The candidate uses identical source/model/container semantics with `-O3 -flto=1 -fprofile-use`. Its compiler execution profile is generated by an instrumented build from 160 development games (10,970 plies), deterministically chosen from `data-r13/dev.uci-bundle` after excluding exact normalized full-game matches in all three timing datasets. Sorting is by SHA256; no candidate speed metrics affect selection. The compiler profile trains code generation only, not probability coefficients. Common starting positions may naturally occur in both development and timing games.

The instrumented executable runs mode3's standard speed command (warm-up and three iterations per direction). Fresh `.gcda` files are required; stale files are removed recursively. The final build uses `-Werror=missing-profile -Werror=coverage-mismatch`, and completed successfully. The initial script's nonrecursive profile-file check was corrected for the compiler's nested output directory, and the full instrumented/training/final build was rerun with fresh counts. Timing uses only the final uninstrumented profile-use executable.

## Predeclared decision and timing

The primary metric is the equal-dataset geometric mean of paired CLI phase-time throughput ratios. Following the user's aggregate-tradeoff preference, retain PGO as the next research working build if aggregate encode and decode gains are both positive; preserve LTO as fallback and disclose every dataset regression. This is a working-build selection based on exploratory point estimates, not an all-dataset or statistical-significance claim. The rule is recorded in the protocol before timing.

CPU0 is pinned. Four alternating ABBA/BAAB blocks per dataset cover three datasets, 48 actual CLI processes and 12 paired blocks per direction. Each CLI invocation warms then runs three timed encode and decode iterations with validation. Two same-label phase wall durations are summed per block, and throughput ratios are combined geometrically. Builds, training, tests and other benchmarks do not run concurrently with timing. Fixed hardware, serial datasets and short runs limit generalization; do not multiply these gains by earlier studies.

Before timing, the two builds must produce byte-identical archives for all five modes on all three datasets. Each pack validates roundtrip. The candidate also runs the existing 1,226-check suite for empty/short inputs, CRC, truncation, wrong model, LUT invariants and R18 payload identity. Protocol records executable/dataset hashes; source and profile-training evidence are retained alongside raw timing rows.

## Reproduce

```sh
python3 tools/build/build_r19_lto.py --out build-r19-lto
python3 tools/build/build_r19_pgo.py --out build-r19-pgo
python3 tools/benchmarking/benchmark_r19_pgo.py --baseline build-r19-lto/r19_lto --candidate build-r19-pgo/r19_pgo --out fresh-pgo-study
```

The PGO script builds, trains and rebuilds at one fixed output path because compiler profile names depend on build paths. Retained profile files document this run; rebuilding in a new location should regenerate them with the script. No architecture-specific ISA, fast-math or benchmark-test-game training is enabled. The same compiler/source is used for instrumented and profile-use builds. Results from other compilers or machines may differ.

## Measured outcome

| Dataset | Encode gain vs LTO | Decode gain vs LTO |
|---|---:|---:|
| r19 | -5.534% | -2.755% |
| r18 | -3.078% | -2.887% |
| r17 | -0.857% | -5.711% |

Equal-dataset geometric mean gains are encode -3.175% and decode -3.794%. Both directions regressed on every dataset in this run. PGO fails the predeclared aggregate selection rule and is not retained as the working build. LTO remains the accepted baseline. All 15 byte-identity cases and 1,226 existing checks passed; correctness does not imply a performance gain. This development-profile choice was tested once, with no heldout-guided profile retuning.
