# DMT12 — 반복 탐색·새 자료 검증·속도 비교 결과

실행일: 2026-10-22. **기본 프로파일 234 유지. 새 압축률 우선 연구 후보는 250 (`r12-joint-all`).**

## 확인된 변화

- 이전 개발용 인간 기보 3묶음: **12,994 → 12,842비트**, 152비트(1.17%) 절약. 실제 파일 합계 1,710 → 1,691바이트.
- 새 공개 표준 대국 100판: 개발/선택/최종 검증을 합산하면 **30,903 → 30,399비트**, 504비트(1.63%) 절약. 이것 전체를 독립 검증으로 세면 안 된다.
- 후보 고정 후 처음 측정한 최종 검증 25판: **8,547 → 8,417비트**, 130비트(1.52%) 절약. 실제 파일 **1,112 → 1,096바이트**(1.44% 절약).
- 기존 234의 확률·스트림은 바꾸지 않고 후보 체크 계산 중복 제거와 정확한 특징 점수 조회표를 추가했다. 일반 빌드는 자료에 따라 속도 이득이 다르다. LTO는 추가 선택 옵션이다.
- 통계 조회 캐시와 PGO는 일관된 우위가 없어 기본 설정에서 제외했다. 실험 재현을 위한 코드와 기록은 보관했다.
- 모든 국면·모든 자료에서 압축률과 속도 목표를 동시에 달성한 것은 아니다. 특히 WCC13의 250 미들게임은 **4.08981 bit/반수**, Human4 미들게임은 234보다 소폭 악화됐다.

## 1. 실제 반복 과정

| 단계 | 변경/비교 | 판단 |
|---|---|---|
| 1차 | 다섯 특징군 및 전체 조합, 학습률 1/2/4: 18개 설정 | 기물별 착지 공격·수비 상태 조합이 유망 |
| 2차 | 특징군, 국면, 학습률, 감쇠를 조합한 24개 설정 | 모든 국면의 기물별 조합 보정이 개발 자료에서 우세 |
| 선택 | 개발 자료에서 추린 4개 설정을 새 선택 25판에서 비교 | 실제 파일이 가장 작은 설정 고정 |
| 최종 검증 | 고정한 250을 보류한 새 25판에 최초 적용 | 실제 비트와 파일 크기 모두 감소 |
| 속도 1 | 후보 가중치와 관계 특징의 체크 계산을 한 번으로 합침 | 바이트 유지, 기본 경로에 반영 |
| 속도 2 | 10비트 특징 점수를 두 개의 5비트 표로 계산 | 정수 합과 완전 동일, 기본 빌드에 반영 |
| 속도 3 | 예측/학습 사이 opportunity 통계 노드 참조 재사용 | 코퍼스별 역전, 기본 OFF |
| 속도 4 | 개발 자료로만 컴파일러 PGO 실행 프로파일 생성 | 여러 경우 일반 빌드보다 느려 기본 미사용 |
| 속도 5 | LTO로 번역 단위 사이 최적화 | 인간 기보의 234에서 유용, 다른 경우 손실도 있어 선택 옵션 |

서로 다른 확률 설정은 총 **42개**다. 선택 단계의 4개는 그중 재사용한 설정이다. 모든 설정과 실패 결과를 `benchmarks-r12/round1_*.csv`, `round2_*.csv`, `selection.csv`에 기록했다. 속도는 각 회차 원시 CSV를 보관했으며 유리한 한 회차만 남기지 않았다.

## 2. 새 모델의 구조

234의 기존 전문가 혼합·보정 기반에, 기물과 후보 수의 특징을 함께 학습하는 작은 범주형 잔차 모델을 추가했다. 단순히 목적지를 먼저 쓰도록 부호화 순서를 바꾼 방식은 아니다.

각 합법 후보는 다음 다섯 특징군에서 하나씩, 총 5개의 항목을 활성화한다.

1. 기물 종류 × 상대적 목적지 랭크: 48항목.
2. 기물 종류 × 목적지 중앙성: 24항목.
3. 기물 종류 × 착지점의 공격·수비 상태: 24항목.
4. 기물 종류 × 이동 거리: 48항목.
5. 기물 종류 × 포획·체크 여부: 24항목.

총 168개 가중치를 국면별로 분리해 온라인 학습한다. 모델·분수 누적 상태는 약 3KB이며, 학습은 이미 복원된 수만 사용한다. 오프라인 학습 가중치나 엔진 탐색은 추가하지 않았다. 고정한 설정은 `families=31, rate=4, alpha=100, phase_mask=7, base=234, decay=1024수, cap=32`다.

이 설정을 고른 근거와 동결 기록은 `frozen-candidate.json`에 있다. 최종 검증 이후 확률 설정은 바꾸지 않았다. 이후의 컴파일러·조회 최적화는 압축 바이트가 같음을 별도로 확인했다.

## 3. 자료 분리와 한계

Lichess 공개 계정 `DrNykterstein`의 표준 대국 100판을 내려받아 합법성과 표준 시작 포지션을 검사했다. 기존 번들과 완전히 같은 수열 및 새 자료 내부 중복은 제외했다. 정규화한 UCI 수열의 SHA-256 정렬로 다음처럼 **모델을 새 자료에 적용하기 전에** 분리했다.

- 앞 50판: 새 개발 자료, 4,072반수.
- 다음 25판: 후보 선택 자료, 2,104반수.
- 나머지 25판: 최종 보류 자료, 2,294반수.

100판에는 52개의 서로 다른 플레이어 이름이 등장하지만, **모든 대국에 한 계정이 포함되어 있어 스타일·레이팅 편향이 있다**. 기록의 레이팅 범위는 1,820~3,289다. 이 표본만으로 보통 인간 기보 전체에 대한 일반화나 통계적 유의성을 입증했다고 주장하지 않는다.

Kasparov–Deep Blue 1997의 6판(519반수)은 별도 확인 자료다. 인간끼리의 대국 표본으로 세지 않았다. 원본 PGN은 결과 ZIP에서 제외했고, 수열과 출처·게임 헤더·해시를 `data-r12/`에 보관했다. 모든 수열은 python-chess와 프로젝트 코덱의 합법 수 경로로 확인했다. 기보의 수열만 압축하며 PGN의 선수·대회 헤더는 압축 대상이 아니다.

자료 출처:

- [Lichess 공개 기보 API](https://lichess.org/api/games/user/DrNykterstein?max=100&moves=true&tags=true&clocks=false&evals=false)
- [python-chess의 Kasparov–Deep Blue PGN](https://raw.githubusercontent.com/niklasf/python-chess/master/data/pgn/kasparov-deep-blue-1997.pgn)

`tools/analysis/audit_r12_data.py`는 106개 수열의 해시·반수·자료 간 중복을 재검사한다. 다운로드 이후 표본을 다시 받지 않아도 동봉한 수열로 모든 압축 실험을 재현할 수 있다.

## 4. 실제 압축 결과

화살표는 234 → 250. 비트는 산술 부호화 페이로드이며, 바이트는 헤더·게임 길이·CRC를 포함한 실제 아카이브 크기다.

| 자료 | 반수 | 페이로드 비트 | 실제 바이트 | 비트 절약 |
|---|---:|---:|---:|---:|
| Human23 / 개발 재사용 | 1718 | 6497 → 6430 | 850 → 841 | 1.03% |
| Human4 / 개발 재사용 | 496 | 1949 → 1929 | 263 → 261 | 1.03% |
| WCC13 / 개발 재사용 | 1155 | 4548 → 4483 | 597 → 589 | 1.43% |
| 새 개발 50판 | 4072 | 14755 → 14536 | 1912 → 1884 | 1.48% |
| 새 선택 25판 | 2104 | 7601 → 7446 | 990 → 970 | 2.04% |
| 최종 검증 25판 | 2294 | 8547 → 8417 | 1112 → 1096 | 1.52% |
| Random48 / 통제 | 4607 | 23507 → 23500 | 3001 → 3000 | 0.03% |
| Kasparov–Deep Blue 6판 / 별도 | 519 | 2145 → 2135 | 288 → 286 | 0.47% |

WCC13의 전체 페이로드 평균은 약 3.938 → 3.881 bit/반수로 낮아졌지만 미들게임만 보면 4.12274 → 4.08981이다. 국면별 수치를 전체 평균과 혼동하면 안 된다. Human4 미들게임은 4.14312 → 4.14946으로 악화됐으며 오프닝·엔드게임의 절약이 전체 개선을 만들었다.

Human23, WCC13, 새 개발 자료를 역순으로 부호화한 검사에서도 250의 비트가 줄었다. 역순 검사는 새로운 독립 대국이 아니며 `order_checks.csv`에 별도로 기록했다.

## 5. 속도 — 최신 LTO 비교 회차

단위는 **인코딩 / 디코딩 반수/초**. 같은 회차의 별도 실행 3회 중앙값이다. 이전 R11은 같은 기본 모델 234의 수정 전 스냅샷이다.

| 자료 | 이전 R11/234 | 일반 빌드/234 | LTO/234 | 일반 빌드/250 | LTO/250 |
|---|---:|---:|---:|---:|---:|
| wcc13 | 60,675 / 62,236 | 58,894 / 62,071 | 64,967 / 64,100 | 59,081 / 59,930 | 56,913 / 58,868 |
| new_sealed | 63,989 / 60,907 | 70,064 / 71,342 | 72,301 / 72,492 | 63,007 / 62,937 | 64,617 / 66,312 |
| random48 | 53,912 / 54,618 | 57,952 / 58,932 | 54,783 / 55,140 | 48,671 / 51,961 | 45,076 / 43,680 |

LTO/234는 이 회차에서 WCC13 약 6.5만, 새 최종 검증 약 7.2만 반수/초를 기록했다. 반면 LTO/250은 Random48 등에서 일반 빌드보다 느렸다. **LTO를 모든 모델의 기본값으로 강제하지 않는다.** 250은 더 작은 파일을 얻지만 추가 보정 비용이 있다.

한 번의 호출은 워밍업 후 5 trial × 인코딩/디코딩 각 4회이며 중앙값을 반환한다. 이 호출을 3회 독립 실행하고 순서를 번갈아 배치했다. Wall clock과 process CPU clock을 모두 기록했다. 공식 측정 중 이 작업의 다른 빌드·검사 작업은 병행하지 않았다. 빌드는 같은 GCC `-O3` 계열이며 `-march=native`는 사용하지 않았다.

공유 환경에서 실행 회차 간 차이가 크다. 예를 들어 WCC13 일반 234와 이전 R11의 순위가 회차에 따라 바뀐다. 따라서 일정 비율의 보편적 속도 향상이나 모든 자료에서의 60~70K 달성을 주장하지 않는다. 초반 회차, 캐시 회차, PGO 회차 및 LTO 회차의 원시 CSV와 요약을 모두 보관했다. PGO의 계측 빌드 실행 수치는 학습용이며 속도 비교에 사용하지 않았다.

## 6. 무손실·호환성·오류 검사

- 기존 249개 프로파일(0~248): Human23와 Random48에서 R11 원본 아카이브와 **실제 바이트 단위로 일치**.
- 조회표, 통계 캐시, PGO, LTO의 각 변형: 251개 프로파일(0~250)을 두 코퍼스에서 원본 경로와 비교, **모두 바이트 일치**.
- 기존 기본 모델 검사, DMT10 집중 64개 프로파일, DMT11 신규 6개, 골든 9개, CRC·결정성 검사: PASS.
- DMT12: 빈 아카이브/빈 게임, 새 선택 25판, 랜덤 합법 12판, 다양한 구성, 고정/구성형 페이로드 일치, alpha=0과 234의 페이로드 일치: PASS.
- CRC 오류, CRC를 다시 계산한 잘못된 구성과 버전, 잘린 구성형 아카이브: 거부 확인.
- 후보 생성 최적화: 별도 오라클 빌드에서 원래 후보 생성기의 순서·가중치·분류·관계 특징과 비교해 PASS. 빠른 합법성 검사도 기준 검사와 대조했다.
- 커널 검사: 공격 맵 543,150개, 정수 나눗셈 160,000개, 특징 점수 131,072개 비교: PASS. 캐슬링·앙파상·승격 포함.
- 프로젝트 core, DMG8, phase 테스트: PASS. 최종 재현 스크립트의 32개 압축 결과는 기록한 비트·바이트 수와 다시 일치했다.
- 이전에 미완료였던 전체 `dmg_mid_roundtrip`의 실행 파일도 이번에는 완주: **251개 전 프로파일**, 빈 아카이브/빈 게임, Human23, 랜덤 8판, 결정성, CRC, 전치·골든·구버전 호환성 모두 PASS. `full_mid_tests.log` 참조.

CMake가 없는 환경이라 실제 빌드와 검사는 동봉한 g++ 빌드 스크립트로 수행했다. **CTest 명령 자체를 실행한 것은 아니다.** 해당 전체 왕복 테스트 실행 파일은 g++로 빌드해 별도로 완주했으며, 구버전 249개 바이트 전수 비교와 집중 검사도 수행했다. 다른 CPU·컴파일러에서 같은 속도나 성능 순위를 보장하지 않는다.

## 7. 스트림과 사용법

기본 234와 기존 0~248의 의미는 그대로다.

- ID 249 / `DMTC`: 구성형 연구 모델. 특징군·학습률·혼합 강도·국면·기반·감쇠·상한의 7바이트를 헤더에 기록한다. 복원에 외부 설정이 필요 없다.
- ID 250 / `DMTD`: 이번에 고정한 `r12-joint-all`. 설정은 ID에 고정되어 7바이트의 추가 설정 헤더가 없다.

구버전 `DMTB`는 243~248만 허용한다. 새 ID를 이전 버전 마커로 바꾼 스트림은 거부한다. 향후 새 설정을 250에 덮어씌우면 안 된다.

일반 빌드와 재현:

```bash
python3 tools/build/build_r12.py --out build-r12
python3 tools/reproduction/reproduce_r12.py --build build-r12 --out reproduced-r12 --search --full
./build-r12/dmg_mid main
./build-r12/dmg_mid pack fast.dmt examples/heldout/*.uci
./build-r12/dmg_mid pack r12-joint-all compact.dmt examples/heldout/*.uci
./build-r12/dmg_mid unpack compact.dmt recovered
```

LTO와 같은 회차 비교:

```bash
python3 tools/build/build_r12_lto.py --out build-r12-lto
python3 tools/benchmarking/benchmark_r12.py --build build-r12 --lto-build build-r12-lto --out benchmark-r12 --audit
```

일반 CMake 경로도 유지한다. LTO는 `-DCMAKE_INTERPROCEDURAL_OPTIMIZATION=ON`으로 선택할 수 있다. `DMT_FEATURE_LUT` 기본 ON, `DMT_CACHE_OPPORTUNITY` 기본 OFF다. 원본 후보 생성기는 `DMT_FAST_JOINT_CANDIDATES=OFF`로 비교할 수 있다. `DMT_VERIFY_JOINT_CANDIDATES`, `DMT_VERIFY_REUSE`, `RMC_VERIFY_LEGAL_FAST`는 검사용이다.

PGO와 통계 캐시의 재실험 도구도 포함했지만 기본 권고가 아니다. `build_r12_pgo.py`는 새 개발 자료와 Random48만 컴파일러 프로파일에 사용한다. 코덱의 학습 가중치를 오프라인으로 바꾸는 방식이 아니다.

과거 보고서는 당시 기록으로 보관했다. `reference-dmt10/`와 `reference-r11/`은 비교에 사용한 수정 전 소스다. 최신 동작과 결과는 이 문서와 `benchmarks-r12/`를 기준으로 한다.
